General Warehouse troubleshooting

A symptom-led runbook for recurring operational problems in Microsoft Fabric Warehouse. Start with the affected layer, gather proportionate evidence, and choose the relevant investigation path.

01 / START HEREScope, safety and access

This guide targets Microsoft Fabric Warehouse. Do not substitute SQL Server, Azure SQL, Fabric SQL Database, Lakehouse endpoint, or Synapse Dedicated SQL Pool diagnostic scripts merely because some DMV names look similar.

Start with the symptom

Cannot connect, lost access, failed execution, slow query, busy capacity, failed load, conflicting writes or unexpected results each needs a different first check. Use the scenario selector; a lock inventory is not a universal prerequisite.

Follow the evidence across layers

Client and identity settings, Fabric status, pipeline runs, SQL history, live requests and capacity metrics answer different questions. Locking and idle transactions are included as scenario J, alongside nine other paths.

Before operational use. These read-only examples follow public Microsoft documentation and have not been executed in your environment. Have an authorized administrator validate the applicable scripts in a nonproduction Warehouse before using them operationally. Use your approved SQL tools and authentication. The runbook does not schedule collection or perform remediation; conclusions require evidence from the affected environment.

Confirm the approved SQL endpoint, database, caller's workspace role, incident window in UTC, and approved execution tool. If SQL cannot connect or the capacity rejects diagnostics, use client, service and capacity evidence first. When SQL is available, use a separate diagnostic connection in SSMS, the Fabric SQL query editor, or your approved integration. No SQL is executed by opening this document.

Scope: common investigation patterns, not a measured ranking of incident frequency or an exhaustive error catalog. Detailed Lakehouse/Spark diagnostics, Power BI model tuning, network policy changes, recovery operations and service-level root-cause analysis require the appropriate specialist teams. Use the scenario boundaries to route the investigation to the responsible team.

03 / SYMPTOM SELECTORStart here: what is failing, and where?

Capture the last known good time, first failure time, timezone, affected Warehouse, affected users/tools, exact error and recent changes. Establish whether the issue affects one user, one query, one load, the whole Warehouse, or multiple items on the same capacity. The sequence below is a practical triage order, not a frequency ranking.

Choose the right evidence surface

Client/pipeline logs: connection failures, retries, orchestration and end-to-end duration. Query Insights / Monitor: completed SQL, failures and comparisons. Live DMVs: requests and waits visible now. Capacity Metrics: capacity-wide usage and rejection, including when SQL diagnostics cannot run. None is a substitute for all the others. [24]

Do not turn diagnosis into a disruptive experiment. No automatic load reruns, pause/resume, scaling, cache clearing, table rebuilds, statistics updates, grants, isolation changes or session termination. Even SELECT queries consume resources; approve expensive reproductions and business-table scans separately.

04 / SCENARIO AConnection and authentication failures

Use when: the client cannot establish a SQL connection, authentication fails, or one tool works while another does not. Start outside SQL: an inaccessible Warehouse cannot supply DMV evidence.

  1. Confirm the destination. Copy the SQL connection string from the intended Fabric item and supply the Warehouse name as Initial Catalog / Database. Do not use a browser URL as the SQL server. Current documentation says an omitted Initial Catalog connects to master; connection success alone does not prove the intended Warehouse was reached.
  2. Separate authentication from authorization. Use a supported Microsoft Entra authentication flow for the actual user or service principal. SQL authentication is not supported. Record the tenant/account context and failure stage, not passwords, tokens or complete secret-bearing connection strings.
  3. Check the client and network path. Record tool/driver version and encryption/authentication settings. Warehouse uses MSSQL/TDS over TCP 1433, not HTTPS on that port. Ask the network owner to check applicable service tags, endpoint rules, private-network policy and protocol inspection without disabling controls.
  4. Compare a working path. With approval, try the same identity and Warehouse in another supported client or approved machine. A portal success and desktop failure is useful isolation evidence, not proof that all network paths are healthy. MARS and SQL Server linked-server connections are not supported.
A1 - Minimal connection and database-context check

Run only after a SQL connection succeeds. No user tables are read. Stop and reconnect to the intended database if the result does not match the approved target.

Connection context; does not prove object or monitoring access
SELECT
    SYSUTCDATETIME() AS collected_at_utc,
    DB_NAME() AS connected_database,
    DB_ID() AS connected_database_id,
    USER_NAME() AS database_user,
    @@SPID AS diagnostic_session_id;

Decision / owner: authentication failure goes to the identity/client owner; network/path differences go to the network owner; connection succeeds but object access fails goes to C. If the connection previously worked and many users now fail, use B and F. [13]

05 / SCENARIO BIntermittent disconnections and service unavailability

Use when: connections drop after previously working, the item is temporarily unavailable, or several tools fail during the same interval.

  1. Determine the scope. Record first/last failure, successful intervals, affected identities and clients, and whether other Warehouses/items on the same capacity are affected. Keep approved client request/correlation identifiers.
  2. Check control-plane context. Ask the capacity owner to confirm active/paused state and capacity availability. Review published Fabric service health and known issues in the approved support channel. Record observations; do not assert an outage from one failure.
  3. Classify the actual error. Documented examples include 24804 and 6005 for temporary loss during deployment/reconfiguration, and 6008 for a temporary connection interruption. Error 24801 indicating exceeded capacity limits belongs to F, not a generic network diagnosis.
  4. Use bounded recovery. For the manual transient-connection troubleshooting path, Microsoft advises waiting 5-10 minutes before a fresh connection and retry. Application owners should use bounded backoff appropriate to the documented error, not immediate repeated retries. Record recovery time and recurrence.
Unknown write outcome: loss of a connection or a client timeout does not prove a write was rolled back. Before replaying ingestion or a transaction, the owner must establish its outcome and retry/idempotency boundary. This guide does not replay writes.

Decision / owner: persistent cross-client failure on an active capacity needs a support handoff with error, UTC window and approved item/request identifiers. Single-path failures return to A. Do not pause/resume a capacity as a diagnostic reset. [14] [13]

06 / SCENARIO CPermission denied, missing objects and context mismatch

Use when: connecting succeeds but an operation is denied, an expected table/view is not visible, or behavior differs by identity.

  1. Confirm database and naming. Use A1, then check the schema-qualified object name and deployment target. Review recent rename/deployment changes. An object missing from Explorer is not proof that it was deleted.
  2. Review access layers with the owner. Fabric Read item permission enables connection; required SQL object permissions still matter. ReadData and ReadAll are different permissions. A report share, source-storage entitlement or successful sign-in is not proof of Warehouse object access.
  3. Inspect the caller's effective access. Use C1 for the specific object, and have an authorized owner independently confirm existence and intended permissions. Catalog visibility can be restricted. After an approved permission change, allow documented propagation time (up to two hours) and sign in again.
  4. Distinguish security effects from broken data. Row-level security, column-level security and masking can explain different results. Preserve those protections; do not remove policies or sensitivity labels to make a test succeed.
C1 - Object visibility and effective permissions

Replace dbo.YourTable with the exact object. Empty metadata, NULL IDs and a permission-function error must be recorded as such; they do not independently prove absence.

Inspect metadata and permissions; no access changes
SELECT
    DB_NAME() AS connected_database,
    OBJECT_ID(N'dbo.YourTable') AS visible_object_id;

SELECT entity_name, subentity_name, permission_name
FROM sys.fn_my_permissions(N'dbo.YourTable', N'OBJECT');

Decision / owner: the Warehouse/security owner resolves missing entitlement or deployment mismatches through least-privilege change control. Monitoring-view access follows the separate access table; do not recommend SELECT grants as a monitoring bypass. [20] [6]

08 / SCENARIO ESlow queries, regressions and first-run variability

Use when: one query shape is slower than its baseline, execution varies between runs, or the first run after inactivity is much slower. Compare equivalent work first; do not assume locking or a platform regression. Broad slowdown across query shapes also needs scenario F. [15]

  1. Preserve the actual symptom. Record whether the application saw a slow response, cancellation, timeout or failure. Capture the client timestamp with timezone, approved error text/code and statement identifier. A client timeout is not, by itself, proof of the server's final status.
  2. Check the historical execution. Use the connected Warehouse's Query Insights, after completion and allowing for ingestion lag. Preserve status, error_code, raw timestamps and total_elapsed_time_ms. A missing row is not automatically a successful run or evidence the request never ran.
  3. Compare like-for-like runs. Use query_hash within history to find similar query shapes. Check parameters, data volume, concurrent workload, recorded application and cache outcome. The same shape may process very different amounts of data.
  4. Add context, not a premature cause. Align the request window and pool with pool-pressure events. Review CPU allocation and scan volumes. Inspect current cache configuration and relevant table statistics only where useful.
  5. Escalate unresolved cases with evidence. Provide a small, approved comparison of an affected run and a suitable baseline, including identifiers, timestamps, errors and evidence gaps. State hypotheses separately from observations.

09 / SCENARIO FBroad slowdown, workload concurrency and capacity rejection

Use when: many unrelated queries slow down together, scheduled workloads overlap, or new connections/operations are rejected with capacity-limit errors.

  1. Check the capacity-wide view first. Ask an authorized capacity administrator to review Capacity Metrics for the same incident window: item consumption, competing Fabric workloads, overutilization, carry-forward and rejection. Do not attribute all usage to the affected Warehouse.
  2. Distinguish two signals. is_pool_under_pressure is a SQL pool signal; Fabric capacity throttling is a capacity policy. Pool pressure is not proof of throttling, and a capacity rejection need not have a matching pool-pressure row. Use example 10 with the affected SQL pool if SQL access is available.
  3. Account for workload admission. Documented Warehouse error 24801 says the organization's Fabric compute capacity exceeded its limits. Background rejection can also prevent DMV queries. Do not report these unavailable views as zero activity or try to bypass the rejection.
  4. Compare demand with a baseline. Record active requests if visible, arrivals, query mix, load schedules and completed-run duration. Check recurring job overlap and repeated expensive query shapes. Completed-history counts are not instantaneous concurrency.
F1 - Historical request volume and outcome by hour

Use this only when history is accessible; replace the UTC window. The counts cover visible, ingested completed executions grouped by submission hour, not all arrivals, active concurrency, CPU utilization or all capacity consumption. Allow up to 15 minutes for recent history to appear.

SQL workload trend; 200 groups plus sentinel
SELECT TOP (201)
    CAST(submit_time AS date) AS submit_date_utc,
    DATEPART(hour, submit_time) AS submit_hour_utc,
    status,
    COUNT_BIG(*) AS recorded_request_count,
    AVG(CAST(total_elapsed_time_ms AS decimal(19,2))) AS avg_elapsed_ms,
    MAX(total_elapsed_time_ms) AS max_elapsed_ms
FROM queryinsights.exec_requests_history
WHERE submit_time >= CAST('2026-09-25T00:00:00' AS datetime2)
    AND submit_time < CAST('2026-09-26T00:00:00' AS datetime2)
GROUP BY CAST(submit_time AS date), DATEPART(hour, submit_time), status
ORDER BY submit_date_utc, submit_hour_utc, status;

Decision / owner: the capacity and workload owners evaluate demand reduction, scheduling, query tuning or capacity changes through change control. Smoothing is consumption accounting, not a queue-time measurement. Inflight operations are not throttled midway by the documented policy; new operations are subject to admission/rejection. Do not infer the cause of a running query's delay solely from a throttling chart. [17]

Decision / owner: data engineering fixes the identified source, mapping, orchestration or target issue. For COPY performance, public guidance suggests file sizes around 100 MB-1 GB and parallel loading across different tables; these are tuning guidelines, not mandatory limits or a recommendation to change a running workload blindly. Before any rerun: confirm which batches committed and whether the load is idempotent. A full replay can duplicate data. Never remove a sensitivity label or weaken source access policy as a troubleshooting shortcut.

11 / SCENARIO HWrite-write conflicts and aborted transactions

Use when: a concurrent modification fails with an update-conflict message, including documented errors 24556 or 24706. This is distinct from a request that is currently waiting on a lock. [16]

  1. Capture the conflict precisely. Record exact code/text, affected operation/table, transaction or batch boundaries and statement IDs. Use D1 and 07-08 for available outcomes.
  2. Reconstruct overlapping writers. Ask the workload owner for concurrent UPDATE, DELETE, MERGE, TRUNCATE and related transaction schedules. Different rows in the same table can still conflict; do not assume non-overlapping predicates guarantee safety.
  3. Distinguish conflict from blocking. An aborted transaction may leave no active waiter. A missing current blocking edge does not refute the recorded conflict. If live operations are waiting, investigate J separately.
  4. Review the retry unit. The owner must verify which transaction failed and which work succeeded, including external side effects. Replay only the appropriate failed unit with bounded delay/backoff and an idempotent design; do not retry just the last statement of an unknown multi-step transaction.

Decision / owner: the ETL/application owner reviews writer overlap and shorter transaction scope, then validates any scheduling or retry change. Do not change isolation levels as a remedy: Fabric Warehouse enforces snapshot isolation. Do not attribute a conflict to background compaction or another service activity without supporting evidence. Recurring conflicts without an identified overlap need an approved support handoff.

12 / SCENARIO IMissing, stale, duplicated or unexpected results

Use when: a load reports success but expected rows are absent, SQL and a report disagree, values differ by user, or duplicates/incorrect aggregates appear. Stop unnecessary writes and preserve the comparison before trying a refresh or reload.

  1. Define the expected result. Record a business key or batch approved for the investigation by the data owner, expected/actual count or value, data cutoff, timezone, source version and exact filters. Compare equivalent data snapshots; a changing source cannot serve as an unqualified baseline.
  2. Find the first layer that diverges. Trace source files/rows to pipeline batch, Warehouse table/view, semantic model and report. Check connected database and schema. A pipeline success is not proof that every expected source partition or row was loaded.
  3. Review transactions and data logic. Check committed load outcomes, retries, watermarks, deduplication, join multiplicity, NULL handling, conversions and rounding. Snapshot isolation can explain an older view within an existing transaction; have the owner establish its boundary rather than changing it from diagnostics.
  4. Account for security. RLS, column access and masking can intentionally produce different outputs. Have the security owner compare authorized contexts; do not grant elevated access or disable protections as a test.
  5. Separate Warehouse from BI behavior. If direct SQL is correct but a report is not, record the actual model/source and storage mode. For Import, check the last successful refresh. For DirectQuery, inspect its generated query and filters. For Direct Lake, inspect model refresh/framing and any applicable fallback with the BI owner; do not assume every report request runs Warehouse SQL.
I1 - Optional bounded business-data reconciliation

Separate approval required: unlike the metadata examples, these read a business table. Replace the illustrative table, key, batch column and value with the owner's approved schema. Use a small relevant batch and an agreed source baseline. Aggregates may scan many rows despite small output; do not run a full-table scan during an incident without an overhead review.

Illustrative batch count and duplicate-key candidates
SELECT COUNT_BIG(*) AS visible_batch_row_count
FROM dbo.YourTable
WHERE LoadBatchId = 'approved-batch-id';

SELECT TOP (201)
    BusinessKey,
    COUNT_BIG(*) AS occurrences_in_batch
FROM dbo.YourTable
WHERE LoadBatchId = 'approved-batch-id'
GROUP BY BusinessKey
HAVING COUNT_BIG(*) > 1
ORDER BY occurrences_in_batch DESC, BusinessKey;

Adapt the key to the real business grain (possibly multiple columns). Equal counts do not prove equal contents. No duplicate candidates in one batch do not prove global uniqueness. A 201-row duplicate result is truncated, and row-level security may restrict what is visible.

Constraints are not data-quality enforcement. Warehouse primary, unique and foreign-key constraints are supported as NOT ENFORCED. Their presence is not proof that keys are unique or relationships valid. Do not delete duplicates or rebuild/reload a table from this diagnostic guide. [21]

Decision / owner: data engineering owns the first source/load/table mismatch; the BI owner owns a model/report-only mismatch; the security owner confirms intended filtering. If an approved minimal reproduction still shows an unexplained mismatch under the same identity and data/transaction context, escalate it. Result-set caching is designed to maintain consistency by invalidation; an unexpected result is not evidence that clearing a cache will fix it. [8] [22]

13 / SCENARIO JLocking, blocking and idle open transactions

Use when: requests wait on locks, schema operations stall, catalog reads appear blocked, or downstream work points to a blocker. Start with current edges and lock modes, not an assumption that all writes block reads. Fabric uses snapshot isolation, but schema locks can still block operations. [16]

Idle-blocker evidence pattern: a blocked request points to a positive blocker session ID, supporting lock evidence is visible, and that blocker has an open transaction with no observed active request. A sleeping session or an open transaction on its own is not enough. Use scripts 00-04 for this branch.

  1. Start from a victim request. Record database, session/request IDs, request start time, blocking_session_id, raw wait type and current wait duration. Do not treat every nonzero or special blocker value as an ordinary lock owner.
  2. Follow the observed edges upstream. Use script 03 to identify each blocker. Retain missing owners and cross-database leads. Stop a branch at a repeated node or 32 edges; label cycles, missing visibility, row caps and depth limits as unresolved, not as a confirmed deadlock.
  3. Inspect the blocker session, not the victim's transaction count. Use blocker_open_transaction_count or the session inventory. Session-driven joins retain an idle owner that has no request row. A visible endpoint with no further upstream edge is a head-blocker candidate, not a confirmed root cause.
  4. Corroborate lock impact. Inspect the victim's wait/conversion and the blocker's held resources and lock modes in the target database. Keep raw WAIT, CONVERT, GRANT/GRANTED and unfamiliar statuses. Matching a resource ID alone does not establish an incompatible blocking pair.
  5. Assess idle duration carefully. For a no-active-request candidate, the interval since last_request_end_time is an idle-age proxy only if the timestamp is valid, nonfuture, and its time basis is known. Review candidates at or above 300 seconds; retain unknown ages. This is not transaction age.
  6. Hand off to the workload owner. Include observed impact and gaps. Transaction completion, undo, or session cancellation must follow a separate authorized operational process. Do not automate any of those actions from this runbook.
Important: a completed statement in Query Insights does not prove its surrounding transaction ended or its locks were released. Current transaction and lock state require live evidence.

Prevention review with the application owner

Review transaction boundaries, error handling and connection reuse so work does not leave transactions open. Keep transaction scope short and review competing schema/data operations. Changing transaction behavior or scheduling requires owner approval and separate change control.

Decision / owner: if the blocker is active, examine its request and workload rather than calling it idle. If the evidence is incomplete, label the chain unresolved. The workload owner owns transaction handling; the administrator owns any approved intervention. An aborted write conflict belongs to scenario H and is not proof of a current blocking chain.

15 / SHARED EVIDENCEPool pressure, caching and statistics

Pool pressure is event-based, not a continuous sample

queryinsights.sql_pool_insights records configuration, capacity and pressure-state changes. Pressure changes are logged when sustained for at least one minute, and logging pauses during inactivity. Match the execution's sql_pool_name and time window; do not assume every request used the same pool. An empty or NULL pool name can occur for requests that do not need distributed execution. [7] [5]

Review the last available state before the window as well as events within it. No event inside the window does not establish that there was no pressure. If the baseline is absent, the starting state is unknown; do not invent it.

Distinguish result-set reuse from data-scan caches

The per-execution result_cache_hit values mean 2 = used an existing result-set cache, 1 = created a result-set cache, and 0 = not applicable for creation or usage. Do not label a historical row "cache disabled." A value of 0 has multiple possible explanations. Memory/disk scan figures describe data-scan caching and are not the same thing as result-set reuse. [8]

Current database setting; not historical configuration

This setting applies at collection time. It does not reconstruct the setting at the time of an older execution. Enabling result-set caching does not guarantee eligibility or a cache hit for every SELECT. No configuration changes or cache-clearing operations are part of this guide.

Statistics: inspect metadata before forming a hypothesis

Fabric can create and refresh needed statistics at query time, which can contribute to duration. That general behavior does not prove it happened during a particular request. Use the SELECT-only catalog views below; no DBCC command is needed. [9]

12 - Statistics columns and most recent update metadata

Replace dbo.YourTable with the relevant schema-qualified table. This returns visible automatic and user-created statistics and keeps entries without column metadata.

Relevant table metadata; 200 rows plus sentinel
SELECT TOP (201)
    OBJECT_SCHEMA_NAME(s.object_id) AS schema_name,
    OBJECT_NAME(s.object_id) AS table_name,
    s.stats_id,
    s.name AS statistics_name,
    c.name AS column_name,
    sc.stats_column_id,
    s.auto_created,
    s.user_created,
    STATS_DATE(s.object_id, s.stats_id) AS statistics_update_date
FROM sys.stats AS s
INNER JOIN sys.objects AS o
    ON o.object_id = s.object_id
LEFT JOIN sys.stats_columns AS sc
    ON sc.object_id = s.object_id
    AND sc.stats_id = s.stats_id
LEFT JOIN sys.columns AS c
    ON c.object_id = sc.object_id
    AND c.column_id = sc.column_id
WHERE o.type = 'U'
    AND s.object_id = OBJECT_ID(N'dbo.YourTable')
ORDER BY s.stats_id, sc.stats_column_id;

STATS_DATE returns datetime, not datetime2, and can return NULL when no statistics blob exists. Preserve NULL as unknown/unavailable metadata, not "never updated." Empty output can also reflect the object name or metadata visibility. An old timestamp alone is not evidence of harmful staleness. [10]

No automatic tuning: do not change statistics, caching, workload settings or permissions simply because a timestamp is old, an execution is slow, or a pressure event is present. Any proposed change needs an owner-approved hypothesis and separate change control.

Collection rules

  • Default to one pass. Only if persistence assessment is approved, take at most three passes at least 30 seconds apart, without overlapping runs. Do not create polling jobs.
  • These reads are not an atomic snapshot. Keep UTC collection times; match requests using database, session, request ID and start time, and sessions using session ID plus login time where available.

  • Do not infer progress from increasing elapsed time, or infer a stall from a flat elapsed counter. total_elapsed_time is request elapsed time; wait_time describes the current wait, not cumulative blocked duration.
